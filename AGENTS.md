# AGENTS.md — Guía para agentes de IA (Family Wallet)

Webapp familiar para gestionar gastos e ingresos: 3 cuentas (2 personales + 1 común), movimientos con naturaleza propio/común y tags múltiples. Producto en español, uso individual sin login.

## Reglas de oro (leer antes de actuar)

1. **Lee siempre `.specify/memory/constitution.md`**: es la ley del proyecto; todo plan la valida (Constitution Check).
2. **Nada de código de funcionalidad sin spec → plan → tasks aprobados** (flujo Spec Kit). Los fixes triviales (typos, lint) están exentos.
3. **Antes de dar por terminado cualquier cambio de código**: ejecuta `npm run lint`, `npm run typecheck` y `npm run test` y verifica que están en verde.
4. **Respetar estrictamente la dirección de dependencias**: Dominio → Aplicación → Adaptadores. El dominio NUNCA importa nada de Next.js, Drizzle, Zod o la UI.
5. **Nunca hagas commit/push sin petición explícita del usuario** (excepción: los hooks de auto-commit de Spec Kit habilitados por el propietario; ver «Flujo de trabajo Spec Kit»).
6. **Mantenimiento de documentación**: si fijas o descubres una convención del proyecto que no está documentada, actualiza `AGENTS.md` (y `docs/` si aplica) en el mismo cambio. Las decisiones arquitectónicas nuevas se registran como ADR en `docs/architecture/adr/`.

## Arquitectura Interna & Reglas Hexagonales (Invariantes)

El proyecto sigue una arquitectura **Hexagonal (Ports & Adapters)**. Para mantener las capas desacopladas, debes cumplir estas reglas en la generación de código:

- **Dominio (`src/domain/`)**:
  - Contiene Entidades, Value Objects, Excepciones de Dominio y Eventos de dominio (solo cuando estén justificados en el plan).
  - **Cero dependencias externas**: Prohibido importar frameworks (Next.js, React), ORMs (Drizzle) o librerías de infraestructura.
- **Aplicación (`src/application/`)**:
  - Contiene Casos de Uso y **Puertos** (Interfaces de Entrada/Salida).
  - Orquesta la lógica del dominio. Depende únicamente de la capa de `domain`.
- **Adaptadores (`src/infrastructure/` y `src/app/`)**:
  - **Entrada (Inbound)**: Route Handlers y páginas de Next.js en `src/app/` (único directorio que Next.js rutea; adaptadores finos que validan y delegan), Server Actions y componentes UI en `src/infrastructure/primary/`.
  - **Salida (Outbound)**: Repositorios Drizzle, clientes de base de datos, servicios externos.
  - Implementan los puertos definidos en la capa de aplicación.

> **Progressive Disclosure**: Si necesitas crear o refactorizar código de una capa o módulo complejo, consulta la guía de arquitectura detallada y diagramas en `docs/architecture/overview.md` (si existe; si no, la spec del Spec Kit activa es la fuente de verdad).

## Flujo de trabajo Spec Kit

El proyecto sigue desarrollo dirigido por especificaciones. Comandos (en este orden):

```
/speckit.specify    # crea specs/NNN-<short-name>/spec.md (actualiza .specify/feature.json)
/speckit.clarify    # resuelve dudas de la spec (opcional)
/speckit.plan       # genera plan.md, research.md, data-model.md, contracts/, quickstart.md
/speckit.tasks      # genera tasks.md a partir del plan
/speckit.implement  # ejecuta las tareas
/speckit.finish     # cierra el ciclo: mergea la PR (rebase), borra ramas y desactiva la feature
```

- El directorio de feature activo se resuelve desde `.specify/feature.json`.
- **Auto-commits por fase**: los hooks de la extensión git (`before_*`/`after_*` → `speckit.git.commit` en `.specify/extensions.yml`) están habilitados como automáticos; commitean los artefactos de cada fase con mensaje Conventional Commit generado al efecto (`commit_style: conventional` en `.specify/extensions/git/git-config.yml`).
- **PR automática tras implementar**: el hook `after_implement` de la extensión `pr` (`.specify/extensions/pr/`, prioridad 20 — corre tras el auto-commit) hace `git push -u origin feature/NNN-…` y crea con `gh` una PR a `main` (título `feat: <título de la spec>` — Conventional Commit, cuerpo con el Summary de la spec y enlaces a spec/plan/tasks). Es idempotente (si ya existe la PR, muestra su URL) y degrada sin error si no hay rama feature, remote, `gh` o autenticación.
- **Cierre de feature (`/speckit.finish`, extensión `finish`)**: tras revisar la PR, cierra el ciclo con `gh pr merge --rebase --delete-branch`. Guardas: PR abierta, CI verde (`gh pr checks`, una PR sin checks continúa con aviso), fila de la feature marcada «Completada» en el roadmap maestro, árbol limpio y rama sincronizada con su upstream. Después: borra rama local y remota, limpia `.specify/feature.json` (a `{}`, dejando la siguiente feature arrancar limpio) y lo commitea/pushea en `main` como `chore(NNN)`. Aborta con error claro si cualquier guarda falla; nunca fuerza el merge.
- `specs/001-family-wallet/` es el **roadmap maestro**: NO se implementa directamente; las features hijas (`002-...`, `003-...`) desarrollan sus historias.
- Cada `/speckit.plan` valida contra la constitución y justifica desviaciones en Complexity Tracking.
- **Granularidad** (constitución II, v1.2.1): una feature hija comprende por defecto una única US pequeña que entrega valor por sí sola; si una spec termina agrupando varias USs con valor independiente, se divide en features separadas. Agrupar historias en una misma spec es una excepción que decide y justifica el propietario (p. ej. 003: edición y eliminación comparten formulario y recorrido UI).
- **Diagramas de diseño en el plan**: cada `/speckit.plan` incluye diagramas mermaid del diseño congelado: clases del modelo en `data-model.md` (sección «Diagrama de clases»), y componentes por capa + secuencia del happy path en `plan.md` (sección «Diagramas de diseño», definida en la plantilla `.specify/templates/plan-template.md`). Son la foto del diseño de la feature; `docs/architecture/diagrams/` sigue siendo la documentación viva que la implementación extiende reutilizándolos como base.

## Convenciones

- **Idioma**: UI, specs y documentación en español; identificadores de código en inglés (excepto términos de dominio intraducibles, documentados en el glosario del data-model).
- **Ramas**: las features se desarrollan en ramas `feature/NNN-<short-name>` (p. ej. `feature/005-cierre-mensual`), creadas por la extensión git de Spec Kit (`branch_template` en `.specify/extensions/git/git-config.yml`) con el número de la spec a la que corresponden; se integran en `main` tras completar el ciclo.
- **Commits**: Conventional Commits (`feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`).
- **Moneda**: EUR con 2 decimales como céntimos enteros (VO `Money`, ADR 0007); los cálculos monetarios evitan aritmética de coma flotante directa. El formateo `Intl es-ES` vive solo en `src/infrastructure/primary/ui/format.ts`.
- **Tests**: co-localizados junto a su SUT (`*.test.ts(x)`); Vitest con `test.projects` (`node` para dominio/aplicación/infra/actions, `ui` jsdom para componentes). Las Server Actions se mockean con `vi.mock`; los repositorios se prueban contra libsql `:memory:` con las migraciones de `drizzle/`.
- **E2E**: Playwright contra `build + start` con BD aislada determinista (`e2e.sqlite`, recreada por `pretest:e2e`); specs en serie dentro de cada fichero porque comparten estado de BD; además, cada spec debe operar en una combinación cuenta/mes propia para no colisionar con los demás specs, y `workers: 1` fuerza el orden alfabético de ficheros sobre la misma BD — necesario porque la BD compartida es determinista: cada fichero debe encontrar su combinación cuenta/mes en el estado exacto en que la dejó el fichero anterior, y varios specs leen agregados del mes en curso de cuentas que otros escriben (p. ej. `porcentaje-ahorro` A2 depende de los movimientos restaurados por `cuenta-kpi-gasto-personal` G7).
- **Diálogos por fila**: los diálogos de acciones de fila (editar/eliminar) se montan a nivel del componente listado (`grouped-movement-list.tsx`) con el DTO capturado en estado del cliente, nunca dentro de la propia fila; tras `revalidatePath` la fila puede desaparecer del árbol y un diálogo anclado a ella perdería el estado de `useActionState` (toast y cierre nunca llegarían). El estado vacío del listado también se renderiza dentro del propio `grouped-movement-list.tsx` (client), nunca como swap condicional en `page.tsx`: vaciar la vista (p. ej. eliminar el último movimiento visible) desmontaría el listado y con él el diálogo activo. Aplica igual a la vista de administración de etiquetas (`tag-catalog.tsx`, 004): menú ⋮ por fila, diálogos de renombrado/fusión/desactivación a nivel del listado y «Reactivar» como action directa + `useTransition` con toast (familia ADR 0015).
- **Modo de selección y acciones masivas sobre listados (029, ADR 0023)**: la edición masiva vive en el propio listado (`grouped-movement-list.tsx`, client) como estado local `selectionMode`/`selectedIds: Set<number>` — botón «Seleccionar» junto al CTA (solo con movimientos), barra contextual («{n} seleccionados», «Seleccionar todo»/«Ninguno», acción masiva, «Salir de la selección») y `Checkbox` shadcn por fila con área táctil ≥ 44 px (`before:-inset-3.5`) y `aria-label="Seleccionar {nota}"`. **Las filas protegidas no ofrecen checkbox** (hueco del mismo ancho): la exclusión es en origen vía `isProtectedTagSlug` del dominio (módulo puro compartido con el cliente, importado directamente — nunca a través de un puerto). El diálogo de la acción masiva se monta **a nivel del listado** (convención «diálogos por fila») con los ids capturados en estado; el éxito cierra, tuesta y **sale del modo con selección limpia**; la navegación de mes (stepper) desmonta la página y reinicia la selección (no se persiste). El Select del diálogo es controlado + restauración por ref (SC-004) y el guard de éxito se blinda con flag por envío (patrón 014). La escritura masiva baja por un **método de puerto específico** (`MovementRepository.retagMovements`: única sentencia UPDATE con pertenencia cuenta+mes en el `WHERE` e `ids` ajenos descartados sin error — recuento real `{updated}`), paridad `mergeInto` de 004; la action re-valida con Zod (ids como campos repetidos `formData.getAll`) y compone el aviso «{u} de {t}…» con los descartes.
- **Inputs de formulario en diálogos con `useActionState`**: controlados con `useState`, nunca `defaultValue` (patrón `rename-tag-dialog.tsx`, 004). React 19 restablece los inputs **no controlados** al resolverse la action del `<form>`, de modo que un error de dominio (estado `{ status: "error" }`) borraría el valor tecleado por el usuario; el controlado lo conserva (SC-004) y el error se muestra con `role="alert"` + `aria-describedby`. **Matiz RadioGroup (032)**: el `RadioGroup` de Radix escucha el evento `reset` del formulario y fuerza su valor controlado de vuelta al valor de montaje (`initialValueRef`) — tras un error de `useActionState`, el auto-reset de React 19 (que llama `form.reset()` en la fase de mutación del commit) borra el tipo elegido aunque esté controlado, y el `onReset` sintético de React **no** dispara para ese reset interno. Restauración (patrón `movement-form.tsx`): listener propio `addEventListener("reset")` sobre el `<form>` que lee la selección enviada de los radios nativos (`input[name="type"]:checked` — el evento `reset` se dispara **antes** de restaurar valores) y la re-aplica en `queueMicrotask` (corre tras el listener de Radix). El Select de Radix (027) sufre la misma familia y se blinda leyendo el valor de `state.values` mientras el error está activo.
- **Tarjetas lanzaderas con menú de configuración (020, amendado por 008)**: las tarjetas del panel de cuentas (`account-card-grid.tsx`, client) usan el patrón **stretched-link**: `div.relative` con los estilos de tarjeta + `<Link>` que envuelve nombre+etiqueta y se estira con `after:absolute after:inset-0`; el trigger ⋮ (≥ 44 px, `relative z-10`, `aria-label="Configuración de {nombre}"`) queda por encima — el clic en ⋮ nunca navega y el resto de la tarjeta sí, con HTML válido (un `<button>` nunca dentro del `<a>`; el contenido del menú abre en portal de Radix). Desde 008 el ⋮ existe en las **3 tarjetas**: en las personales el primer ítem es «Renombrar miembro» (abre `RenameMemberDialog`, antes que la config) y siguen los ítems de config 018/019/023 (el ítem «Ingreso regular» deriva su estado de la función pura `regularIncomeMenuStatus` sobre el prop `regularIncomes` que `/` lee en servidor); la tarjeta de la común tiene ⋮ con único ítem «Renombrar cuenta» (abre `RenameAccountDialog`). El **nombre mostrado de una cuenta personal es siempre el derivado** «Cuenta de {miembro}» — nunca almacenado (`accounts.name` NULL en personales, migración `0007`): la derivación vive en UNA función de aplicación (`personalAccountDisplayName`) aplicada por `DrizzleAccountRepository.findAll` (`AccountDTO.name` = nombre mostrado), la UI jamás lo concatena ni recalcula (ADR 0020). Los diálogos se montan condicionalmente **dentro de la tarjeta** — excepción consciente y documentada de «diálogos por fila»: las tarjetas son catálogo estable (no desaparecen tras `revalidatePath`), así que el estado de `useActionState` no se pierde; cada apertura es una instancia fresca (patrón 014/018).
- **Categorías del catálogo de etiquetas (026, ADR 0022)**: nivel de agrupación por encima de las etiquetas — taxonomía 1..N etiquetas por categoría con **pertenencia única y obligatoria como atributo de la etiqueta** (`tags.category_id` NOT NULL FK `ON DELETE RESTRICT`; FR-001 por construcción: `Tag.categoryId` obligatoria + `moveToCategory`). La **genérica** se identifica por slug constante (`DEFAULT_CATEGORY_SLUG = "general"` en `src/domain/tag-category/DefaultCategory.ts`, espejo de `SystemTags`): renombrable sin perder su papel, no eliminable; nace en la migración `0008` (backfill del 100 % de las etiquetas existentes) y en el seed. Gestión **solo en `/tags`** (`ListTagCatalog` devuelve `TagCatalogGroupDTO[]` pre-ordenado — genérica primero, resto `localeCompare("es")`, activas primero dentro de grupo; **la UI solo anida**, constitución VII): botón «Nueva categoría», menú ⋮ por categoría (genérica sin «Eliminar…») y «Mover a categoría…» como primer ítem del menú de cada etiqueta (la fila protegida «Aportación Común» tiene menú con ese único ítem — es movible); los diálogos se montan a nivel del listado (convención «Diálogos por fila»); `MoveTagToCategory` es no-op con la misma categoría y su diálogo excluye la actual. Revalidación de categorías acotada a `revalidatePath("/tags")` (no viven en ninguna otra vista); los tags siguen revalidando layout (Select «Etiqueta», ver 027). **Intocables por diseño**: `Movement`, agregados de lectura, `/summary`, `/annual`, formularios y KPIs — la categoría no computa en ningún agregado (FR-008); toda etiqueta nueva nace en la genérica vía `CreateTag`.
- **Jerarquía y creación única (027, amend de 026)**: `/tags` presenta un **árbol contenedor** — cada categoría es un `section aria-label="Categoría {nombre}"` con `rounded-lg border`, cabecera dentro (nombre + cardinal + ⋮) y `ul` de filas sangrada dentro (`tag-catalog.tsx`) — y tiene **una única vía de creación**: el botón «Nueva etiqueta» de la cabecera abre `CreateTagDialog` (montado a nivel del listado) con nombre + **categoría padre opcional**; la **inferencia de tipo vive en la frontera**: la action despachadora `createTagEntry` (`create-tag-entry.action.ts`, Zod `{ name, categoryId? }`) rut sin `categoryId` a `CreateCategory` («Categoría creada») y con `categoryId` a `CreateTag` extendido (`execute({ name, categoryId? })`: valida existencia → `CategoryNotFoundError`; sin él → genérica, retrocompatible con 017) («Etiqueta creada»). Jubilados «Nueva categoría» + `create-category.action`/`CreateCategoryDialog` y `ListActiveTags` (sustituido por `ListGroupedActiveTags`, que agrupa, omite categorías sin activas y congela el orden — genérica primera, resto es-ES, etiquetas por nombre — devolviendo `ActiveTagGroupDTO[]`; la UI solo anida). El Select «Etiqueta» de alta/edición (`movement-form.tsx`) es **agrupado**: prop `tagGroups: ActiveTagGroupDTO[]` (página de cuenta hace una lectura por render), «Sin etiqueta» como ítem plano primero (solo ingresos) y un `SelectGroup`+`SelectLabel` por categoría — las cabeceras **no son ítems** (ni clic ni foco ni typeahead: FR-005 por construcción). `TagDTO` queda enriquecido con `categoryId`/`categoryName` para que el inline 017 (`create-tag.action.ts`) fusione la etiqueta nueva en el grupo de la genérica (estado `extraTags` de los diálogos, fin del sort plano; `MovementTagDTO` de filas sin cambios). Guarda de estado conocida: tras un error de `useActionState`, el auto-reset de formularios de React 19 dispara un `change` en el select nativo de Radix que borra el estado controlado del Select — el diálogo lo restaura con un ref de última selección válida (`create-tag-dialog.tsx`); los inputs de texto ya estaban blindados por ser controlados (SC-004).
- **Captación continua (tanda)**: los diálogos de alta continua remontan el **componente de formulario completo** (incluida su instancia de `useActionState`) con `key={savedCount}` desde el padre, nunca el `<form>` interno suelto: el remonte interno pierde el binding de la action prop en el envío siguiente. Los valores estables viajan como `carry` (`{ date, type, nature }`) en estado del padre y se aplican como `defaultValue`/estado inicial del remonte; los variables (nota/importe/tag) nacen vacíos y el foco se programa en el primer campo vacío tras el remonte. El `intent` (`continue|close`) viaja en botones submit HTML (`name="intent"`) y vuelve en el estado de la action; el efecto de éxito se blinda contra re-ejecuciones re-montando el guardado (flag/reset por envío). Patrón fijado por 014 (`create-movement-dialog.tsx`).
- **Captación inline de subentidades (junto a un control del formulario)**: cuando un formulario necesita crear una entidad menor en caliente (p. ej. una etiqueta junto al Select «Etiqueta», patrón «+ Nueva etiqueta» de 017), se usa **action directa + `useTransition`** —sin `<form>` anidado (HTML inválido) ni `useActionState`— porque el valor ya vive en estado local y la action devuelve un **resultado** (`{ ok, tag | message }`), no un estado de formulario: es una consulta, no un envío. El botón que dispara es `type="button"`; Enter en el input se intercepta (`preventDefault`) para no enviar el formulario padre; Escape cancela la captación sin cerrar el diálogo (`data-tag-creation-input` en el input + `onEscapeKeyDown` que hace `preventDefault` en el `DialogContent` cuando el foco está ahí). La disponibilidad inmediata se garantiza con estado `extraTags` **a nivel de diálogo** (padre del remonte `key={savedCount}` de la tanda, igual que `savedCount`/`carry`) + `revalidatePath("/", "layout")` en la action. Excepción documentada al patrón «toda action con `useActionState`» (ADR 0015).
- **Materialización perezosa (ingresos regulares y aportaciones comunes)**: la página de cuenta (`src/app/accounts/[accountId]/page.tsx`) invoca `MaterializeRegularIncomes.ensureForAccountAndMonth` y, a continuación, `MaterializeCommonContributions.ensureForAccountAndMonth` **antes** de leer (dos awaits secuenciales antes del `Promise.all`: cubren listado y KPIs del mismo render); son el **único disparador** de la materialización — los agregados (`/summary`, `/annual`) y los repositorios/use cases de lectura nunca materializan (decisión del propietario 2026-10-12; ADR 0016/0017). La idempotencia vive en el registro de meses de cada agregado (`regular_income_months` / `common_contribution_months`, `UNIQUE (config, mes)` + `ON CONFLICT DO NOTHING` en la misma tx que el movimiento), **nunca** en la existencia del movimiento: así el borrado del movimiento generado es definitivo y las ediciones de config son solo-adelante. `currentMonth` entra como parámetro calculado por el adaptador (`ui/format.ts`), sin puerto Clock.
- **Aportación neta y re-sincronización del mes en curso (021, ADR 0019)**: desde 021 la aportación mensual es un importe **neto** — `ContributionPercentage.netAppliedToCents(ingreso, Σ gastos)` = `max(0, bruto − gastos comunes del mes en la cuenta personal)` — y el materializador de aportaciones **re-sincroniza el mes en curso en la misma lectura** (`ensureForAccountAndMonth`: guardas §1.2.1 de la spec): altas/ediciones/eliminaciones de gastos `nature = "shared"` ajustan el importe del movimiento enlazado vía `movements.update(Movement.recreate(...))` al consultar, sin hooks en el CRUD (las actions ya revalidan la página). El alcance del descuento vive sellado en `MovementRepository.sumSharedExpenseCents` (SUM SQL por cuenta + mes). La fila del registro es dueña del **enlace blando** `movement_id` (migración `0005`, sin FK; filas legacy se resuelven perezosamente por heurística acotada en el repositorio): **retirada** (neto 0) borra movimiento **y fila** (`withdrawMaterialization`; la generación queda reabierta y la aportación reaparece si los gastos bajan), mientras que el **borrado del usuario** deja la fila sin movimiento → no-op definitivo. La guarda `config.active` solo aplica a la generación: desactivar a mitad de mes no congela el ajuste del mes en curso (clarify 2026-10-18). Meses cerrados (`month !== currentMonth`) quedan congelados.
- **Registro manual de la aportación común (032, ADR 0024)**: `common_contribution_months` tiene **dos vías de escritura** que convergen en la misma guarda `UNIQUE (config, mes)`: el materializador (019/021) y el **registro manual** — la aportación de meses pasados es un **tipo de gasto independiente de la frontera UI** (radio «Aportación común» en `movement-form.tsx`, prop `contributionOption: off | available | locked`: solo cuenta personal con config activa), **sin nuevo `MovementType` de dominio**: la action despachadora (`create-movement.action.ts`, Zod `type: "expense" | "income" | "contribution"`) rutúa `contribution` a `RegisterManualContribution`, que compone `Movement.create` con `nature: "personal"` y etiqueta protegida `CONTRIBUTION_TAG_SLUG` implícitas (nunca seleccionables a mano) y persiste movimiento + fila enlazada en **una sola transacción** (`registerManualContribution`: `ON CONFLICT (config, mes) DO UPDATE SET movement_id WHERE movement_id IS NULL RETURNING` — fila huérfana se re-enlaza; fila con enlace → `null` → `ContributionAlreadyExistsError`). Regla «0 o 1» por cuenta y mes: el borrado **manual** elimina movimiento y fila en la misma tx (reversible) y la edición congela identidad (solo importe, nota y fecha); el materializador y las configs quedan intactos y el KPI sigue leyendo el registro (`GetMonthNetContribution`). El **ahorro** de meses pasados sigue sin vía (feature futura).
- **Bloque KPIs sticky en cuentas personales (022, amendado por 023 y 024)**: primer uso de `position: sticky` del repo — `AccountMonthKpis` (`account-month-kpis.tsx`) es un **server component presentacional puro** (sin JS, sin estado cliente, sin selector dentro) con `sticky top-0 z-20` y fondo sangrado `-mx-4 px-4 sm:-mx-6 sm:px-6` (cubre el padding de `main`) + tarjeta interior `rounded-lg border bg-card p-4`; se monta como hijo directo de `<main>` solo en cuentas **personales**, entre `MonthStepper` y `GroupedMovementList`, con etiqueta pasiva `monthLabel(month)`. Desde 024 el `dl` tiene **4 métricas** en orden congelado («Aportación común» · «Gasto personal» · «Ahorro del mes» · «Saldo del mes», `grid grid-cols-2 gap-3 sm:grid-cols-4` — móvil 2×2, ≥`sm` una fila; la celda «Gasto personal» es magnitud `formatAmountCents` sin signo ni `text-red-600` y **sin subtexto ni estados**: lectura pura, nunca «Sin configurar»). La fuente de datos es **exclusivamente casos de uso**: la aportación neta llega de `GetMonthNetContribution` (DTO `{configured, amountCents}` sobre los puertos de 019/021, importe = movimiento enlazado, **nunca recálculo**), el ahorro de `GetMonthSavings` (DTO espejo, importe = fila del registro de deducciones, **nunca recálculo**) y el saldo del mes es **neto del ahorro**: la página de cuenta compone las **dos únicas restas de composición** `netMonthBalanceCents = closure.monthBalanceCents − savings.amountCents` y `personalExpenseCents = closure.personalExpenseCents − netContribution.amountCents` (gasto personal del mes: naturaleza propia **excluida la aportación común**; lectura pura sin configuración ni materialización — 024) y se las pasa calculadas (la UI jamás recalcula ni resta — constitución VII; desde 025 `GetMonthlyClosure` sobrevive sin panel visible como **fuente interna de composición** de los KPIs: ambos números salen del mismo `MonthlyClosureDTO` leído una vez por render, y difieren exactamente en el importe deducido y en la aportación excluida, respectivamente).
- **Apartado informativo con registro de meses congelado, sin movimiento (023)**: variante del patrón de materialización perezosa de 018/019 (ADR 0016/0017) para cantidades **informativas que no son movimientos** (hoy: el ahorro por miembro). La idempotencia y el congelado viven en una tabla registro propia (`savings_allocation_months`, `UNIQUE (config, mes)` + `ON CONFLICT DO NOTHING RETURNING` en tx de **un solo INSERT**) que **congela el importe** (`amount_cents`) en el momento de registrar: el KPI lee esa fila (`GetMonthSavings`), **nunca** recalcula, y no existe borrado del mes. **Sin re-sync del mes en curso** (diferencia deliberada con 021): la base es plana sobre configs (porcentaje sobre el ingreso bruto regular), así que un mes ya consultado jamás cambia por consultas posteriores; la reactivación resetea `activatedAtMonth` y el hueco inactivo no se deduce. La guardia de configuración consulta **existencia** de ingreso regular (paridad 019); el requisito de **activo** aplica solo al deducir (no-op sin registrar el mes si falta — mes abierto). `MaterializeSavingsAllocations.ensureForAccountAndMonth` es el **tercer await secuencial** de la página de cuenta (tras 018/019, antes del `Promise.all`) y **nunca** toca `movements` ni computa en agregados (resumen/anual intactos).
- **Página de cuenta = vista operativa (025)**: `/accounts/{id}` muestra únicamente cabecera, stepper ‹ mes/año ›, bloque «KPIs del mes» (solo personales) y listado agrupado — no existen las regiones «Balance de {cuenta}» ni «Cierre de {mes}» (componentes, puerto `getBalance` y helper `monthEndIsoDate` jubilados con sus tests; SC-004). La consulta agregada vive en `/summary` y `/annual`; la coherencia de los KPIs es por construcción (`GetMonthlyClosure` como fuente interna, ejecutado solo en personales con el patrón de lectura condicionada).
- **BD**: `db.sqlite` en dev; la URL se puede sobreescribir con `DATABASE_URL` (así funcionan los e2e). Migraciones solo por script (`npm run db:migrate`), nunca en runtime serverless; en producción (Turso) se ejecutan desde local como paso pre-deploy con `drizzle.prod.config.ts` y `TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN`.
- **Seed**: idempotente (`onConflictDoNothing` sobre claves naturales); datos editables en `src/infrastructure/db/seed-data.ts`. Desde 026 también siembra `SEED_CATEGORIES` (la genérica) por slug y resuelve su id para sembrar los `SEED_TAGS` con `category_id` (las categorías van primero; paridad con la migración `0008`).
- **Comentarios**: no se añaden comentarios salvo petición explícita; el código se explica por sí mismo y la intención vive en specs/plan.
- **Importación de hoja mensual (028)**: página propia `/import` (nav «Importar», `GlobalNav active="import"` sin `month`) con asistente cliente de dos pasos (`import-sheet-wizard.tsx`): (1) cuenta + mes + fichero CSV y (2) previsualización con totales, filas ignoradas/erróneas, etiquetas nuevas y tabla — la UI **nunca** calcula totales ni mapea: renderiza `SheetImportPreviewDTO`. El parser CSV es **propio** (RFC 4180 estricto, cero dependencias) contra `SHEET_COLUMNS` congelada (las 13 cabeceras de la hoja mensual como datos) en `sheet-csv.ts`; el mapeo de tipos y la validación por fila viven en el **núcleo puro** `buildSheetImportPlan` (`src/application/import/sheet-import-plan.ts`), compartido por `BuildSheetImportPreview` y `ConfirmSheetImport` — la confirmación **re-parsea y re-valida en servidor** (recalcula el plan fresco; `{status:"invalid"}` → «La previsualización ya no es válida…» y vuelta al paso 1). La persistencia todo-o-nada (FR-005) vive en el puerto `SheetImportRepository.persist(ExecutableImportPlan)` (`application/import/SheetImportRepository.ts`), con la `db.transaction` en el adaptador `DrizzleSheetImportRepository` (etiquetas nuevas primero — activas, en la genérica, slug con sufijo `-2…` por paridad con `CreateTag` —, luego `Movement.create` autoritativo por movimiento dentro de la misma tx; cualquier error revierte todo). `Movement.create` es la única vía de validación/escritura (FR-006): el núcleo la ejecuta por fila con `TagId(-1)` centinela nunca persistido cuando la etiqueta se creará. La action `importSheetAction` es directa (familia ADR 0015, extendida: el `File` viaja como argumento desde estado del cliente porque un file input no puede ser controlado — SC-004) con `useTransition`; `revalidatePath("/", "layout")` solo en el éxito de confirmación. Cualquier cambio de cuenta/mes/fichero tras previsualizar descarta la previsualización en cliente. **Sin deduplicación entre importaciones** (PoC): la previsualización con totales es la comprobación previa del usuario. Dominio, esquema, migraciones, materializaciones y agregados intactos (FR-007).
